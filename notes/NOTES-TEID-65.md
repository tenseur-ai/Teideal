# TEID-65 implementation notes

The contract was internally consistent enough to implement without changing its stated boundaries. The following small gaps were resolved conservatively:

- The `syncWorker.ts` architecture bullet lists `advanceWatermark`, while the file-layout section and step 3 place it in `syncHealth.ts`. It is implemented and exported from `syncHealth.ts`; `syncWorker.ts` calls it after every persisted page.
- `parseAndImportInvoiceCsv` is specified with a three-count return type, while the route must also return `csv_import_id` and the storage schema requires a filename even though the function has no filename parameter. The function returns the three required counts plus `csv_import_id` and stores the stable filename `invoices.csv`; the multipart route remains responsible for accepting the uploaded file.
- A `{since, cursor:null}` watermark can mean either “not started” or “exhausted” if the entity key's presence is ignored. During bounded backfill, an absent entity key means not started and a present key with a null cursor means exhausted. Once all entities are exhausted, `completeSync` advances every entity's `since` to the attempt start for subsequent incremental polling.
- The old sync-health behavior exposed the latest attempt's start as `last_sync_at`, but T5 requires a later failure not to erase the prior successful timestamp. The query now prefers the latest successful completion and falls back to the latest attempt time only when a connector has never succeeded, preserving the existing TEID-98 failed-only test behavior.
- T7 asks for a network disconnection for CSV import, although CSV import performs no network request in production. The automated case runs Stripe, CSV import, and `csv_mock` connector-contract instances against an unreachable target and verifies distinct connector-attributed health messages; this exercises the shared failure path without adding a production network call to the CSV importer.
- Scheduled remote polling is limited to `connector_type='stripe'`. CSV imports are marked backfill-complete when their tenant-scoped landing connector is created because they have no remote system to poll. `csv_mock` remains an explicit test/framework connector rather than a production scheduled connector.
- The sandbox had no installed npm dependencies and outbound package installation is unavailable. The multipart lock entries were therefore added from published package metadata rather than regenerated by npm; CI should still verify them with its normal `npm ci` step.

No UI, raw Stripe API-key path, Metronome/Orb/Lago connector, or changes to the TEID-38 Stripe customer-matching path were introduced.

## TEID-65.1 follow-up

- Incremental Stripe polling retains TEID-65's `created[gte]` lists so newly created records remain covered, and adds a separately watermarked Events pass for post-create changes. The exact filtered event set is `invoice.updated`, `invoice.finalized`, `invoice.paid`, `invoice.voided`, `charge.refunded`, and `credit_note.created`.
- The Events pass stores its `{since,cursor}` checkpoint under `cursor_high_water.events`; the existing entity keys and 24-month list-based backfill are unchanged.
- Updates to old Stripe prices and subscriptions are still not observable through their created-based incremental lists. This is the known gap expressly left in scope by TEID-65.1; no speculative broader reconciliation pass was added.
